# Internationalization (i18n)

Every user-visible string in Course Core comes from a message catalog. The product ships in
English (`en`) and Hebrew (`he`, right to left). This document is the contract for everyone who
converts a view, adds a string or adds a locale. Follow it exactly; the CI check enforces most of
it. Hebrew wording follows the [glossary](i18n-glossary.md).

## Where things live

| What | Path |
| --- | --- |
| Supported locales (the one list), pseudo-locales, negotiation | `packages/i18n/src/locales.ts`, `packages/i18n/src/negotiate.ts` |
| Runtime: translator, ICU-subset messages, formatting, bidi helpers | `packages/i18n/src/*.ts` (`@course-core/i18n`) |
| React bindings (React DOM and React Native) | `packages/i18n/src/react.ts` (`@course-core/i18n/react`) |
| Admin catalogs | `apps/admin/src/i18n/messages/<locale>/<namespace>.json` |
| Admin wiring: `useT`, `useI18n`, `useFormatters`, `MessageKey`, `LocaleProvider` | `apps/admin/src/i18n/` |
| Learner catalogs | `apps/learner/src/i18n/messages/<locale>/<namespace>.json` |
| Learner wiring (same names), `LocaleRoot` (direction per platform) | `apps/learner/src/i18n/` |
| Generated catalog index (never edit) | `apps/<app>/src/i18n/catalog.ts` |
| Hardcoded-string baselines | `apps/admin/i18n-baseline.json`, `apps/learner/i18n-baseline.json`, `packages/visuals/i18n-baseline.json` |
| Check script and its tests | `scripts/i18n-check.mjs`, `scripts/i18n-check-tests.mjs` |
| Glossary lint rules (forbidden synonyms, documented exceptions) | `scripts/i18n-glossary.json` |
| API locale preference and workspace default | `services/api/src/locale.ts`, migration `087_locale_preferences.sql` |
| Glossary | `docs/i18n-glossary.md` |

`@course-core/i18n` has no runtime dependencies (React is an optional peer for `./react`). It is
a registered module (`scripts/modules.mjs`) built with `tsc`; its tests run with `npm test` in
`packages/i18n`.

## Catalogs

### One namespace per source file

A namespace is one JSON file per locale. **Each source file uses exactly one namespace, named
after the file**: the base name without extension or platform suffix, first letter lower-cased.

| Source file | Namespace | Files |
| --- | --- | --- |
| `apps/admin/src/views/ReviewsView.tsx` | `reviewsView` | `apps/admin/src/i18n/messages/{en,he}/reviewsView.json` |
| `apps/admin/src/domain/errors.ts` | `errors` | `apps/admin/src/i18n/messages/{en,he}/errors.json` |
| `apps/learner/src/connected/GateDecision.web.tsx` | `gateDecision` | `apps/learner/src/i18n/messages/{en,he}/gateDecision.json` |
| `apps/learner/src/components/CodeEditor.tsx` and `CodeEditor.web.tsx` | `codeEditor` (shared by platform variants) | |
| `apps/admin/src/domain/providerSetup.ts` and `apps/admin/src/text/providerSetup.ts` | `providerSetup` (same base name: one owner converts both) | |

The namespace files for every file that has hardcoded strings today already exist (as `{}`) and
are registered in `catalog.ts`. A conversion therefore edits only its own source files, its own
namespace files and its own baseline lines, so parallel conversions do not conflict. A file may
use keys of another namespace that already exist (for example `localeSwitcher.label`) but never
adds keys to another file's namespace. Do not create a shared "common" namespace; duplicates of
short words across namespaces are fine and keep conversions independent.

If a file that has no namespace yet needs one, create `messages/en/<ns>.json` and
`messages/he/<ns>.json` (both may be `{}`) and run `node scripts/i18n-check.mjs --sync`, which
regenerates `catalog.ts`. If two branches both added namespaces, resolve a `catalog.ts` conflict
by running `--sync` again.

### Format and key naming

Each namespace file is a flat JSON object of key → message, formatted by Prettier (2-space
indent, one key per line):

```json
{
  "title": "Answer reviews",
  "empty.title": "Nothing to review",
  "empty.body": "New answers appear here when a learner submits them.",
  "error.STALE_REVISION": "This review changed since you opened it."
}
```

- The full key used in code is `<namespace>.<key>`, e.g. `reviewsView.empty.title`.
- Keys are dot-separated segments of `[A-Za-z][A-Za-z0-9_]*`. Use lowerCamelCase segments for
  UI structure (`filter.status`, `dialog.confirm`), and the API's own SCREAMING_SNAKE code for
  error messages (`error.LOGIN_FAILED`) so a template literal can select them.
- Name keys by meaning and place, not by English text: `submit`, not `saveAndContinueButton`.
- One key per complete sentence or label. Never build a sentence from several keys or by
  concatenating translated text with other text; word order differs between languages. Use
  arguments, plural/select and tags instead.
- English values keep the current English text exactly, so existing tests keep passing.

### Types

`MessageKey` (from `src/i18n` in each app) is the union of every English key. `t()` only accepts
a `MessageKey`, so a misspelled or missing key is a TypeScript error. For a key chosen at runtime,
build it with a template literal and cast, and keep the literal prefix in the template so the
unused-key check sees it:

```ts
const key = `adminApp.role.${role}` as MessageKey;
return i18n.has(key) ? i18n.t(key) : role; // has() avoids reporting a missing key
```

### Hebrew catalog, pending keys

Every English key must exist in `he/<ns>.json`, or be listed in that file's `"$pending"` array:

```json
{
  "title": "בדיקת תשובות",
  "$pending": ["empty.body"]
}
```

A pending key falls back to English at runtime and is reported by the check (it does not fail).
Conversions in this repository translate everything they convert; `$pending` is for keys added
when a translator is not available. Remove a key from `$pending` when you translate it.

## Using translations in code

```tsx
import { useI18n, useT, useFormatters } from "../i18n";

function ReviewsHeader({ count, learner }: { count: number; learner: string }) {
  const t = useT();
  const i18n = useI18n(); // t, rich, number, currency, date, time, dateTime, relativeFrom, list, locale, lang, dir
  return (
    <header>
      <h1>{t("reviewsView.title")}</h1>
      <p>{t("reviewsView.waiting", { count })}</p>
      <p>{i18n.rich("reviewsView.help", undefined, { link: (children, key) => <a key={key} href="#help">{children}</a> })}</p>
      <bdi>{learner}</bdi>
    </header>
  );
}
```

- Components call `useT()` / `useI18n()`. Pure helpers (validators, error mappers) take a
  `t: Translate` parameter; the app's `englishTranslator()` is only a default for callers that
  have not been converted yet.
- A component rendered without the provider (a unit test of one component) gets English. App
  roots always render `LocaleProvider` (`apps/admin/src/main.tsx`, `apps/learner/App.tsx`).
- Machine codes from the server (roles, states, kinds) are mapped to keys
  (`<ns>.role.<code>`); show the raw code only as the fallback for an unknown value. The admin
  `Status` badge names common states itself from `ui.status.<code>`; pass `label` for a state
  that needs wording of its own.
- `useFormatters()` (admin) replaces the deprecated `money()` and `when()` in
  `components/ui.tsx`.

## Message syntax

An ICU MessageFormat subset (`packages/i18n/src/message.ts`):

| Syntax | Meaning |
| --- | --- |
| `{name}` | Argument. Strings are inserted as is (isolated in right-to-left locales, see Bidi); numbers and dates are formatted for the locale. |
| `{n, number}`, `{n, number, integer}`, `{n, number, percent}` | Number formatting (`0.85` with `percent` is `85%`). |
| `{d, date}`, `{d, date, short\|medium\|long\|full}`, `{d, time, short}` | Date or time of a `Date`, ISO string or epoch milliseconds. |
| `{n, plural, =0 {…} one {…} two {…} other {# …}}` | Plural. `#` is the formatted number. `other` is required. |
| `{n, selectordinal, one {#st} two {#nd} few {#rd} other {#th}}` | Ordinal plural. |
| `{kind, select, owner {…} other {…}}` | Select by a string value. `other` is required. |
| `<link>text</link>`, `<br/>` | Tags, rendered by `rich()` handlers; `t()` keeps only their text. |
| `''`, `'{literal}'` | ICU quoting. An apostrophe followed by any other character is literal, so Hebrew geresh (צ'אט) needs no escaping. |

Plural categories come from `Intl.PluralRules` for the active locale. English uses `one` and
`other`. Hebrew uses `one`, `two` and `other` in current CLDR (older data also had `many` for
20, 30, …); write Hebrew plurals with `one`, `two` and `other`, and `=0` where "none" reads
better. A translation may use categories English does not, and vice versa; only argument and tag
names must match across locales.

## Formatting numbers, dates, currency and relative time

Format with the active locale through the translator, never with `toLocaleString()`,
`toLocaleDateString()` or `new Intl.*("en-US")`; the check flags those.

| Need | Use |
| --- | --- |
| Number | `i18n.number(1234.5)`; inside a message `{n, number}` |
| Percent | `i18n.percent(0.85)`; `{n, number, percent}` |
| Currency | `i18n.currency(12.5, "USD")`; admin `useFormatters().money(cents)` |
| Date / time | `i18n.date(iso)`, `i18n.date(iso, "long")`, `i18n.time(iso)`, `i18n.dateTime(iso, options)` |
| Server timestamp in UTC | admin `useFormatters().when(iso)` (zone name localized) |
| Relative time | `i18n.relativeFrom(iso)` ("לפני 3 שעות"), `i18n.relativeTime(-1, "day")` ("אתמול") |
| List | `i18n.list(["a", "b"])` ("a ו-b") |

Pseudo-locales format like English. Digits stay Latin in Hebrew.

## Bidirectional text

The page direction follows the UI locale. Text whose direction is not the UI's must be isolated:

- **User-supplied and course text** (names, titles, answers, notes, course and section titles):
  render in an element with `dir="auto"` or `<bdi>`, e.g. `<td dir="auto">{course.title}</td>`.
  The admin's shared components take the direction for such text: `<Card titleDir="auto">`,
  `<Dialog titleDir="auto">` and `<Field labelDir="auto">` (a course's own prompt as a label).
  In React Native use `writingDirection` only when the language is known.
- **Identifiers, codes, digests, URLs, file names, versions, emails, JSON and code blocks**:
  always left to right inside right-to-left text: `dir="ltr"` on the element (`<code dir="ltr">`,
  `<pre dir="ltr">`, `<span className="mono" dir="ltr">`). Inside a plain string (an
  `aria-label`, a `title`), use `isolateLtr(value)` from `@course-core/i18n`.
- **Message arguments** are isolated automatically in right-to-left locales: string arguments
  are wrapped in FSI…PDI. Do not add marks yourself. Use `stripBidiControls` in tests that
  compare text.
- Never concatenate a translated string with user text; pass the user text as an argument.
- Form inputs for free text get `dir="auto"`; inputs for codes, URLs, emails and passwords get
  `dir="ltr"`.

## Right-to-left layout

- **CSS logical properties only.** `margin-inline-start/end`, `padding-inline-*`,
  `border-inline-*`, `inset-inline-start/end`, `text-align: start/end`, `float: inline-start`.
  Physical `left`/`right` are allowed only for things that must not mirror (a chart axis, a
  media scrubber). The existing stylesheets were converted (`apps/admin/src/styles.css`,
  `apps/admin/src/components/inspector.css`, `apps/learner/src/connected/connected.css`).
- Flexbox and grid follow the direction automatically; do not reverse them by hand.
- **Directional icons mirror**: back/forward arrows, chevrons that point along the reading
  direction, "next"/"previous", undo/redo, indentation. Add `className="flip-rtl"` (admin) or
  `connected-flip-rtl` (learner) to the icon or glyph. Icons that do not mirror: play/pause,
  check marks, clocks, search, external-link arrows that point up-right, logos, numbers.
- Do not use letter-spacing or uppercase transforms that only make sense in Latin script for
  Hebrew text (`[dir="rtl"] … { letter-spacing: 0 }` is already applied to eyebrows).
- **React Native styles** use `marginStart`/`marginEnd`, `paddingStart`/`paddingEnd`,
  `start`/`end`, `borderStartWidth`, and `textAlign: "auto"` (or omit it). Never `marginLeft`,
  `left`, `textAlign: "left"`. Mirror directional icons with
  `transform: [{ scaleX: dir === "rtl" ? -1 : 1 }]` using `useI18n().dir`.

### Learner direction: per tree, no restart

The learner app sets direction per tree rather than with `I18nManager.forceRTL`, which needs an
app restart and changes global state:

- Web (`src/i18n/LocaleRoot.web.tsx`): `<html lang dir>` follows the locale on every change;
  react-native-web resolves start/end styles as CSS logical properties under it.
- Native (`src/i18n/LocaleRoot.tsx`): the root `View` gets `style={{ direction }}`; Yoga lays
  the whole subtree out right to left, so `start`/`end` styles and flex rows mirror at once.
- Never read `I18nManager.isRTL` (it stays false); read `useI18n().dir`.

## Locale selection

Supported locales are `SUPPORTED_LOCALES` in `packages/i18n/src/locales.ts`; the API, both apps
and the check read that list. The UI locale is chosen in this order:

1. the user's saved preference (`app_users.locale`, set from the language switcher);
2. the request's languages: `Accept-Language` on the server, `navigator.languages` in the client;
3. the workspace default (`workspaces.default_locale`, an owner setting);
4. English.

In the clients (`initialClientLocale`, `reconcileServerLocale` in `negotiate.ts`):

- Before sign-in: a `?locale=` override, then the choice stored on this device
  (`localStorage["course-core:locale"]`), then the browser languages, then English.
- After sign-in, `GET /api/me/locale` answers. A saved preference wins. Without one, a choice
  made on this device is saved with `PUT /api/me/locale`; otherwise the server's resolution
  (which includes the workspace default) applies.
- The switcher (admin: the account bar and the sign-in screen; learner: the profile and the
  sign-in screen) applies the choice at once, remembers it on the device and saves it to the
  account when signed in.

API endpoints (cookie session; mutations need the `X-CSRF-Token` header and a trusted origin):

| Endpoint | Body / result |
| --- | --- |
| `GET /api/me/locale[?workspaceId=]` | `{ preference, locale, source, workspaceDefault, supported }` |
| `PUT /api/me/locale` | `{ locale: "he" \| "en" \| null }` → same shape; `400 UNSUPPORTED_LOCALE` |
| `GET /api/workspaces/:id/locale` (members) | `{ defaultLocale, supported }` |
| `PUT /api/workspaces/:id/locale` (owners) | `{ defaultLocale: … \| null }` → same; audited as `workspace.locale_changed` |
| `GET /auth/session` | `user.locale` is the saved preference or `null` |

## The API speaks codes, not prose

The API returns machine codes and parameters, never English sentences meant for people:
errors are `{ "error": "CODE", "details": { … } }`, states and kinds are enum values. Clients
translate them: put the message under `<namespace>.error.<CODE>` in the namespace of the file
that maps the code (for example the learner's `apiClient` namespace for `CourseApiError`, the
admin's `errors` namespace for `domain/errors.ts`), and pass `details` values as arguments.
When the server must render text itself, it calls `requestLocale(db, request, actorId?,
workspaceId?)` (`services/api/src/locale.ts`) and uses the same fallback order. Do not add new
English prose to API responses; add a code.

Outcomes and findings that are not errors follow the same rule:

- A staff command's `message` is `{ code, params? }` (`services/api/src/staff-messages.ts`),
  worded by the admin's `serverMessages` namespace (`domain/serverMessages.ts`). Receipts
  stored before this hold an English string, which the app shows as is.
- Release checks carry `code` and `params` (`releaseChecks`), course package problems
  `params` (`installCourse.problem.<code>`), study warnings `{ code, params }`
  (`studies.warning.<code>`), and the run inspector role, outcome, context `kind`/`facts`,
  decision codes, artifact `nameCode` and workflow node `facts` (`runText`,
  `runInspectorPanels.node.<kind>`).
- Learner-privacy rules keep their English `label`/`reason` for exported documents; the admin
  words them by `id` (`privacyRules`).
- A learner-model skill state's `explanation` is `{ code, params? }`: the code is the state
  itself, and a gated row adds `independentFamilies` and `requiredFamilies`
  (`services/api/src/learner-model.ts`, worded by the learner's `learnerMemoryPanel.why.<state>`).
- Core's own feedback on a submitted answer (an abstained item without an author explanation, a
  rubric answer sent for review, the built-in code evaluator's result) is `message: { code,
  params? }` on the result (`services/api/src/answer-messages.ts`, worded by
  `answerFeedback.message.<code>`). An author's or an extension's `explanation` stays text in the
  course's language.
- An unknown code is shown inside a translated sentence with the code, never as a bare or
  humanized English guess. `services/api/test/staff-messages.test.ts` and
  `services/api/test/learner-messages.test.ts` check that every code the API can send has an
  English and a Hebrew message.

## Course content language and UI locale

The UI chrome (navigation, buttons, labels, messages) follows the user's locale. Course content
(titles, lesson text, questions, feedback written by authors, generated teaching) is in the
course's language and keeps its own direction, whatever the UI locale:

- Render every container of course content with `contentAttributes(course.language)` from
  `@course-core/i18n`: `<article {...contentAttributes(language)}>` gives `lang` and `dir` for a
  declared language and `dir="auto"` otherwise.
- The released SDK (0.5.0) does not declare a course language yet, so content containers get
  `dir="auto"` today. When the SDK adds a BCP 47 `language` to the course definition, pass it.
- Labels around content stay in the UI locale: "Lesson 3" is UI text; the lesson's title is
  content.
- A course author's strings are never put in the catalogs and never machine-translated by the
  product. Demo fixtures (`src/data/`, visuals demos) are course content.

## Pseudo-locales

| Locale | Effect |
| --- | --- |
| `en-XA` | English catalog with accented letters, about 40% longer, wrapped in `⟦ … ⟧`. Anything without the marks is hardcoded; anything clipped shows where layouts break. The padding is short `~~~~~` runs separated by spaces, so it wraps like words and a view that overflows under en-XA would overflow with a long translation too. |
| `ar-XB` | The same, rendered right to left (text mirrored with RLO). Shows layouts that do not mirror. |

Open any page with `?locale=en-XA` or `?locale=ar-XB` (any build; never saved to the server).
In development and tests the switcher also lists them. They format numbers and dates as English.

## Enforcement

`node scripts/i18n-check.mjs` runs in the "Public source and orchestration" CI job. It needs the
TypeScript compiler API: locally any installed module (`apps/admin/node_modules`) provides it.

### Hardcoded strings

It parses `apps/admin/src`, `apps/learner/src` and `packages/visuals/src` (excluding
`i18n/messages`, `i18n/catalog.ts`, `data/` fixtures, the visuals demo scenes, tests and
declarations) and counts:

- JSX text and string children (`<p>Hello</p>`, `{cond ? "A" : "B"}`);
- string literals and templates in user-facing props: `title`, `label`, `placeholder`, `alt`,
  `aria-label` and the other `aria-*` text props, `accessibilityLabel`, `accessibilityHint`,
  `eyebrow`, `description`, `heading`, `message`, `hint`, `detail`, `text`, … and any prop or
  object property ending in `Label`, `Title`, `Text`, `Message`, `Placeholder`, `Hint`,
  `Description`, `Heading`, `Caption`, `Tooltip` or `Summary`;
- the same names as object properties (`{ label: "Sign out" }`) and parameter defaults;
- sentences passed to display helpers: `setError`, `setNotice`, `setStatus`, `setMessage`,
  other `set…Error/Notice/Status/Message/…` setters, `alert`, `confirm`, `prompt`, `announce`,
  `notify`, and `new …Error("…")`;
- any other sentence-like string (two or more words, starting with a capital or ending in
  punctuation), such as messages in error maps (`{ LOGIN_FAILED: "The username …" }`) and
  labels returned from helpers, except in imports, types, object keys, comparisons, `case`
  labels, `console.*`, selectors, storage keys and media queries;
- locale-blind formatting: `toLocaleString`/`toLocaleDateString`/`toLocaleTimeString` and
  `new Intl.*()` without the active locale.

Allowed without comment: class names, ids, keys, test ids, URLs and emails, lower-case code-like
strings (`nav-link active`, `shell.title`), and UPPER_SNAKE machine codes outside JSX.

A genuine exception gets an inline comment with a reason (at least a few words) on the same line
or the line before. An `i18n-ignore` without a reason is an error.

```tsx
{/* i18n-ignore: product name, not translated */}
// i18n-ignore: developer diagnostic, never shown to people
// i18n-ignore-file: developer-only debug page   (first lines of a file; whole file)
```

### Baseline: counts only go down

Each surface has `i18n-baseline.json` with the number of violations per file. The check fails
when a file's count rises or a file not in the baseline has violations. It also fails when a
count drops and the baseline was not lowered, so the baseline only shrinks. Commands:

| Command | Use |
| --- | --- |
| `node scripts/i18n-check.mjs` | The CI check: strings against the baselines, plus catalogs. |
| `node scripts/i18n-check.mjs --report apps/admin/src/views/ReviewsView.tsx` | List each remaining violation with line and column (a path prefix works too). |
| `node scripts/i18n-check.mjs --update` | Lower the baseline to the current counts. Never raises a count; a fully converted file stays at `0`. |
| `node scripts/i18n-check.mjs --summary` | Counts per surface and directory. |
| `node scripts/i18n-check.mjs --sync` | Regenerate `src/i18n/catalog.ts` after adding a namespace. |
| `node scripts/i18n-check.mjs --prune` | Remove `0` entries. Coordinator only, after parallel branches merged. |
| `node scripts/i18n-check.mjs --init` | Write the baseline for a newly added surface. |

Baseline entries are separated by blank lines so that branches lowering different files merge
without conflicts. Do not reformat, reorder or prune the file in a conversion branch; only
`--update` it.

**Every count above zero needs a reason.** A file that keeps baselined strings has an entry under
`"reasons"` in the same baseline file (at least a sentence: what the strings are and why they are
not catalog keys yet). The check fails for a file above zero without one, so the remaining set
stays small and explained. `--update` keeps a reason while its file is above zero and drops it
at zero.

Current state: the admin and learner apps are at zero, so any new hardcoded string in them fails.
Visuals keeps its older scene-authoring diagnostics (VisualErrors with stable codes that no app
shows to people) with reasons: moving that English into the visuals error catalog changes the
released visuals bytes, so it ships with the next visuals version.

### Catalogs

The same command checks every surface catalog: valid JSON and key names; every English key is
used somewhere in the surface's source (as a string literal, or under a template-literal prefix
such as `` `signIn.error.${code}` ``); every English key exists in each other locale or is in
`$pending`; no locale has keys English lacks; `$pending` lists only missing keys; every message
parses; and each translation uses the same argument and tag names as English. `catalog.ts` must
match `--sync` output.

### Glossary

The same command fails when a message uses a synonym the [glossary](i18n-glossary.md) forbids,
such as מלווה instead of המנחה in Hebrew, or המפקח anywhere in the learner app. The rules live
in `scripts/i18n-glossary.json`: each names a locale, optionally the surfaces it applies to, the
forbidden words (matched as substrings, so Hebrew prefixes are covered), the term to use and the
decision behind it. A genuine exception names the rule and the message as
`<surface>:<namespace>.<key>` with a reason of at least a sentence; an exception that matches
nothing fails until it is removed. English catalogs are not checked.

At runtime a missing translation falls back to English and an unknown key renders as the key;
both are reported once with `console.warn("[i18n] …")` in development and tests, never in
production.

## Converting a view (checklist for conversion work)

1. `node scripts/i18n-check.mjs --report <your files>` to list the strings.
2. Add keys to your file's namespace in `messages/en/<ns>.json` with the exact current English,
   and natural Hebrew in `messages/he/<ns>.json` using the [glossary](i18n-glossary.md).
3. Replace the strings with `t(...)`/`rich(...)`; map server codes to keys; format numbers and
   dates through `useI18n()`; add `dir="auto"` to user and course text, `dir="ltr"` to codes and
   ids; switch physical CSS or RN styles to logical ones; mirror directional icons.
4. Keep existing English test assertions passing. Add or extend a test that renders the view
   in Hebrew (`createAdminTranslator("he")` / `createLearnerTranslator("he")` or a
   `LocaleProvider` with `?locale=he`) when the view has logic around text.
5. `node scripts/i18n-check.mjs --update`, then `node scripts/i18n-check.mjs` must pass.
6. Run the module's typecheck and tests (`npm run typecheck`, `npm test`); for admin also
   `npm run format:check`.

Only edit: your source files, your namespace JSON files, and your files' lines in the baseline.
Do not edit `catalog.ts` by hand, another file's namespace, the glossary (propose additions to
the coordinator), shared shell files (`AdminApp.tsx`, `ConnectedHost*.tsx`, `main.tsx`,
`App.tsx`, `src/i18n/*`) unless they are your assignment.

## Visuals (`@course-core/visuals`)

Visuals 0.5 has its own English catalog in `packages/visuals/src/i18n/messages/` (excluded
from the hardcoded-string count like the apps' catalogs), with no runtime dependency on
`@course-core/i18n`:

- `VisualMessages` has one string or function per user-visible text of the player, inspector,
  device preview, export controls and lazy placeholder; `englishVisualMessages` holds the
  English.
- `VisualPlayer`, `VisualRuntimePlayer`, `LazyVisualPlayer`, `VisualInspector`,
  `DevicePreview` and `ExportControls` take `messages?: Partial<VisualMessages>` (merged over
  English) and, where numbers are shown, `locale?: string` for `Intl.NumberFormat`
  (default `"en"`). `SceneView` takes `dragHint`.
- Every diagnostic is a `VisualCatalogError`: a stable `code`, plus a catalog `key` and
  `params` (`englishErrorMessages` in `src/i18n/messages/errors.ts`), so hosts can translate
  it; its `message` is the English text. Check failures (`runSceneChecks`) and reference-check
  results carry the same `key` and `params` next to `message` (`catalogText`). No source file
  writes English outside the catalog (`test/errors.test.tsx`), and the baseline is zero.
- The inspector shows errors and check failures through `messages.describeError(error)`
  (default: the English `message`). A host translates by `key` with `params` as arguments,
  and falls back to `message` for a key it has no translation for.

The learner app and the admin learner view build `messages` from their `visualMessages`
namespace (`src/components/visualMessages.ts`, `useVisualMessages()`). Their `describeError`
words a catalog error from the `visualErrors` namespace (`error.<key>`, one entry per
`englishErrorMessages` key, with the same parameters) and shows the English `message` for a
key the app does not have; `tests/visualErrors.test.tsx` in each app checks that the English
entries match the visuals' own English. Scene text authored in
a course is content: it follows the course language, not the UI locale.

## Adding a locale

1. Add it to `SUPPORTED_LOCALES` and `LOCALES` (code, direction, native name) in
   `packages/i18n/src/locales.ts`, and run `npm test` in `packages/i18n`.
2. Create `messages/<locale>/` in each app with one file per English namespace (start with `{}`
   plus `"$pending"` listing every key, or translated messages), and run
   `node scripts/i18n-check.mjs --sync`.
3. Extend the glossary with the new language's column.
4. If the language is right to left, nothing else is needed: direction comes from `LOCALES`.
   If its plural rules have categories English lacks, translators use them directly.
5. No migration is needed: the database stores any well-formed tag and the API accepts only
   the supported list.
6. Run `node scripts/i18n-check.mjs`, both apps' unit tests and the i18n browser tests.
